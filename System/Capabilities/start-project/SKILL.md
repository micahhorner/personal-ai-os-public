# Capability — start-project

"Let's start a project" routes here. The floor is deliberately small: a home for the
work (`10 Projects/<Name>/`), one schema-valid project note that says what the work
is and where it stands, and registration so the rest of the system can see it.
Everything richer than that — planning documents, handoff records, decision gates —
is a *method's* layer, and methods are the user's (see the consult line below).

## When

The user names bounded, multi-session work: "start a project for Y", "new project",
"let's build X" where X will outlive this session. A single actionable task is a
to-do item (the to-do route, "add X to my to-do list"), not a project.

## Procedure

1. **Resolve first.** `aios resolve --query "<name>"` — an existing project with
   this name (including drafts, on-hold, or archived) means propose *resuming or
   reviving it*, never a second folder. Search-before-creating is the law here as
   everywhere (Change Control).
2. **Create the folder**: `10 Projects/<Name>/` — the name in the user's own words,
   filename-safe.
3. **Create the project note** `10 Projects/<Name>/<Name>.md` from
   `System/Templates/project.md`, per safe-write: mint the id
   (`aios resolve --mint --type project`), `stage: planned` (or `active` if work
   starts now — `project_stage` vocabulary), `summary` and `## Goal` in one or two
   honest sentences from the conversation, relations (`related`, `depends_on`)
   linked where the conversation named them.
4. **Register**: `aios generate` — the project appears in the generated indexes;
   that is what makes it visible to retrieval instead of a folder nobody re-finds.
5. **Validate**: `aios validate` — the note must be schema-valid before the report.
6. **Say where actions go**: next actions live in the project note's
   `## Next actions` section and, for anything that must surface outside the
   project, on the root `To-Do.md` via the to-do route — items there link back to
   the project note (that link is the resolving path). Per-project to-do files do
   not exist yet; do not invent them.
7. **Name the class for everything else**: any other file that later lands in the
   project folder — a plan, a log, a capture, a scratch draft, whether the user
   writes it or their installed method pack scaffolds it — is *working material*:
   `type: working` with a `working_subtypes` subtype, per
   `System/Schemas/working.yaml` (DEC-096). Typed working files are first-class
   to `validate`, visible to `aios search --project <Name> --domain <domain>` and the Steward, and
   excluded from default knowledge search. Untyped stays legal (a warning, never
   auto-typed); `type: note` under the project layer draws a rolled-up advisory
   (never an error — DEC-082) — knowledge lives in the knowledge folder, so
   propose the retype or the move and let the user choose.
8. **Report** in one line: folder, note id, stage, where actions go.

## Consult line — if a method pack is installed

If the user has an installed method pack (`Packs/`, typically generated by the
Method Kit), **say so and consult its project-start doctrine** for everything above
this floor: its planning artifact, its handoff record, its gates and rituals. The
pack layers on top of this procedure; it never replaces the floor (folder, valid
note, registration). With no pack installed, this floor is the whole procedure —
do not offer to migrate the user to any method, and do not scaffold planning
artifacts they never asked for.

## Fences

- **No plans, no handoff files, no gates from this capability — ever.** Those are
  method-pack territory; scaffolding them here would quietly rebuild one user's
  method as everyone's default.
- One note per project is the schema's model; sub-notes are ordinary notes related
  to it, created through the normal routes.
