# AI Onboarding Procedure

Executed by the Onboarding Guide agent (any runtime at L2 or above — onboarding is guided, single-file, human-confirmed work). The Onboarding Specification is authoritative; on any conflict, it wins. Stage numbers match.

## Session protocol

1. Read the spec, then `80 User/onboarding-progress.yaml`. Missing state → create it (`status: not-started`, stage 1) alongside `80 User/onboarding-answers.yaml`; existing state → confirm the last completed stage with the user in one sentence and resume.
2. One question at a time, in the user's language register. Every question skippable; record skips as `prefer-not-to-say` in the answers file. If an answer sounds sensitive, remind the user they can skip — what enters the vault is their choice (DEC-026). Accept voice answers everywhere.
3. After every stage: run the stage's validation from the spec; write answers to the answers file; write `created_files`, `stages.<n>`, and `resume_instructions` to the progress file.
4. All file creation goes through the standard capabilities (`safe-write`, `ingest-and-connect`) — onboarding gets no special write powers. Never collect secrets or employer-confidential material; warn if offered.

## Stage execution keys

- **1**: **verify read+write FIRST** — have the runtime report the `CONNECT-CHECK.md` token, then write + user-confirm + remove a scratch file under `System/Logs/`; if the write fails, STOP and send the user to `System/Onboarding/Connect Your AI.md` (they are on an uploaded copy or a read-only mirror, and onboarding writes to `80 User/` from here on). Then explain — including the one-line framing (a second brain stores what you know; this stores what you know, how it connects, and how the work gets done on it) and the depth routing: name the Get Started set (Product Overview, Quick Start, Human User Manual) as the path, How the System Works as the next depth, and the reference/architecture docs as the extend-it layer. Offer, never require; no stage waits on reading. Then confirm consent explicitly. Confirm the manifest's `instance_role` is `personal-instance`; on a fresh copy, ask — their yes is the explicit instruction that lets you flip this one protected field. Record it in the progress file. Validation: user names where the kill switch lives.
- **2**: privacy before data — write `80 User/privacy-rules.md`, read the defaults back, get confirmation. This file is a protected object from the moment it exists. Ask the **storage question separately from the sensitivity question** (DEC-092): "must anything never leave this machine — no cloud sync, no hosted backup?" Record the answer as `sync: local-only` guidance (or a `Local Only/` folder), backed by a `.gitignore` rule (`aios validate` cross-checks). Never encode storage intent as `classification: restricted`: that removes content from compliant retrieval but does not physically confine a runtime with native file access. Explain the direct-file limit and keep material the runtime must not technically access outside its filesystem reach.
- **3**: `80 User/profile.md` via template; roles + domains; skip freely.
- **4**: extract 3–5 concrete first jobs (reject vague "help me be productive" — ask for last week's real examples); inventory locations only, no imports. Prior system in the inventory? Run the spec's workstyle block: ask consent BEFORE any scan; scan read-only (never modify their corpus); DRAFT `80 User/workstyle.md` from `System/Templates/workstyle.md` and present it for correction; then ask only what files cannot say — tag meanings, rituals, machinery, the `keep` list (your scan candidates stay proposals until the user binds each one), and the coexistence posture. Migration of their corpus: one offer maximum, never repeated unprompted — name the concrete path when you make it (`aios okf-import` for an Open Knowledge Format bundle, `aios import` for a full external vault; both plan-authored, reversible, landing as draft evidence, never straight into knowledge). **Name where work goes** (v1.8.0): the root `To-Do.md` is the routed home for action items (`manage-todo` — what · why · blocks · resolving path, link-checked on every load); offer **once** to capture one of the just-named jobs as a first item, and seed nothing if they decline.
- **5**: propose from the approved-personalization list only (subtypes in use, vocabulary additions via `80 User/vocabulary-extensions.yaml`, review cadence). Anything structural → "that's an extension for later; noted in unresolved." **Ask the two standards questions** (both skippable): (a) rules for how their outward writing should sound? (b) a standard for how knowledge notes should be built — depth, citations, counterarguments? Yes → write `80 User/voice.md` / `80 User/authoring.md` via safe-write: the rules inline when short, else a one-line pointer to their canonical document (pointer discipline — one canonical home per standard, never a copy of rules that live elsewhere; Onboarding Specification stage 5). The router loads these automatically (`load_if_present`, DEC-036/DEC-063) — no other wiring needed; say so. No → state the shipped defaults apply (safe-write's knowledge-note doctrine; no voice constraint) and that either file can be created later. Record the answers. Run `aios validate` after changes.
- **6**: 3–10 items through `00 Inbox/` + `ingest-and-connect`, narrating each item's journey (classified as X, filed to Y, linked to Z, origin recorded) so the user sees the pipeline on their own material. For an AI chat export or other conversation, narrate the attribution too: voice split measured (`aios measure`), the user's claims taken from the user's own turns, assistant-originated ideas credited or dropped — never filed as the user's (`ingest-and-connect` 3a). Offer once — never press — to capture anything the user knows that isn't in the documents (spoken-context capture in `ingest-and-connect`, labeled with `provided_by` + confidence + verification: unverified). Extract any decision found. Close by confirming the user can say what happened to one item.
- **7**: retrieval test (3 user questions; cite notes by name; abstain where evidence is missing — abstention counts as passing). Safe-write demo: narrate preflight → change → validate (→ journal only when the change is consequential — Kernel §2) so the user sees each step. Record both in state.
- **8**: maintenance prefs; offer pruning of sensitive onboarding answers; **backup setup** — present `System/Documentation/Backup and Recovery Options.md`, let the user CHOOSE from the full menu (never prescribe), explain bad-change-vs-dead-machine + the sensitive-content-off-any-cloud rule, offer to connect the chosen option now (usually a private GitHub remote), record the choice (or defer); tell the user the evidence convention: copies are recorded in `80 User/LAST-BACKUP.txt` (`System/Scripts/backup-clone.sh` writes it after a successful clone; a manual copy takes the one-line command from the options doc) and `aios health` will report local-only content with no recorded off-machine copy — a finding, never an error, and never a false "covered" (no marker = never); if they chose the clone script, offer to run the first backup now; run the **decision review** — present `System/Governance/Active Decisions.md` grouped into user-tunable vs structural-invariant (mark the invariants explicitly; changing one is a system change, not a toggle), walk the user through the tunable set one at a time, and record each amendment as a new dated decision that supersedes the prior one and is journaled (never a silent edit) — **written to the top-level `Decisions/` folder via `record-decision`** (dated slug id, no claimed number), which is also where the user's own decisions live from here on; `Active Decisions.md` is the *product's* register, read and cross-referenced here and **never written to** (product updates overwrite it) — say the boundary out loud once, while both are in view; the user may amend any, all, none, or defer (re-runnable anytime). **Offer the optional Method Kit** module (the `method-kit` capability) — an extended interview that generates the user's own operating-method pack + pack-skills into their user layer; optional (do now / defer / decline); if not completed, record it in `unresolved` (re-surfaced on re-onboarding). **Freshness (awareness only)**: the vault keeps knowledge honest — a changed note's connected neighbors queue for judgment (`aios ripple`), promoted notes carry review dates, cadenced workflows report when overdue; all surfaced in the weekly pass, pre-existing content grandfathered, prose never auto-rewritten (DEC-081/082). **Staying current** (awareness only): tell the user the OS itself updates — when a newer release ships, `aios upgrade` brings `System/` current in one command, notes and customizations untouched, conflicts never silently merged (`System/Documentation/Upgrading.md`); pair it with the backup beat (checkpoint before upgrading). **Mention add-ons** (awareness only): the OS is extensible with packs the user installs anytime by dropping a ZIP in the OS root (`System/Documentation/Add-Ons and Packs.md`), and one already ships installed — `obsidian-bases`, the first third-party pack in `Packs/`, a working example; no further pack is installed here. Note reviewed/amended decisions in the report; write `80 User/onboarding-report.md` listing every created file + unresolved items; set `status: complete`; run `aios health` — must be green.

## Failure handling

Interrupted → state is already saved; nothing else needed. Validation fails → fix within the stage or record in `unresolved`, never advance silently. User overwhelmed → offer to defer any stage (mark `deferred`) — stages 1, 2, and 7 may not be deferred.
