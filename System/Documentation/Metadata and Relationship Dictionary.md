# Metadata and Relationship Dictionary

The complete reserved vocabulary of this vault. `aios.py validate` enforces it: unknown keys fail validation unless prefixed `x_` (the experimentation escape hatch — promote or remove `x_` keys promptly). Allowed values for constrained fields live in `System/Schemas/vocabularies.yaml`; per-class requirements live in the class schemas.

## Identity and core (required on every canonical note)

| Key | Type | Meaning |
|---|---|---|
| `id` | id | Stable identifier, `<type>-<slug>`, immutable (Vault Profile §2) |
| `type` | word | Note class: note, source, entity, project, decision, procedure, output, working (or system-doc) |
| `created` / `updated` | date | ISO 8601 |
| `summary` | text | One or two sentences; what a reader (or context compiler) gets without opening the body |

## Common optional

| Key | Type | Meaning |
|---|---|---|
| `subtype` | vocab (per class) | note: concept/finding/claim/question/lesson · source: document/web/meeting/interview/tacit · entity: person/organization/place/product · working: plan/log/capture/draft/scratch (required there) |
| `status` | vocab `status` | Lifecycle: draft → active → review-due → stale → superseded \| archived |
| `aliases` | list | Alternate names (entities especially) |
| `tags` | list | Sparing, cross-cutting labels; not a taxonomy |

## Relationships (values are stable IDs; wikilink form tolerated)

**Direction rule**: store the relationship **once, in the dependent / derived / newer item**. Reverse views are generated by `aios.py generate` — never hand-maintained.

| Key | Cardinality | Meaning (read as: this note → target) |
|---|---|---|
| `sources` | list | is grounded in this evidence |
| `derived_from` | list | was produced from this material (lineage) |
| `depends_on` | list | operationally depends on this (change → check me) |
| `supersedes` | one | replaces this older record. **You set the reciprocal `superseded_by` yourself** — nothing writes it for you (see below) |
| `superseded_by` | one | set on the OLD record, by the runtime performing the supersede (`safe-write` → *Changing an existing note*). `validate` only **warns** when the old record's `status` is not `superseded`/`archived` — it writes nothing |
| `supports` | list | provides evidence for this claim/finding |
| `contradicts` | list | conflicts with this claim/finding — both records are preserved; contradictions are never silently resolved |
| `related` | list | untyped association |
| `entities` | list | is about these people/organizations/places/products |
| `project` | one | scopes a decision to its project (DEC-095). `links` resolves it like any other reference — a dead value is an error, not a note |

These ten are exactly `REL_FIELDS` in `links.py`; nothing outside that list is resolved, and nothing
in it is skipped. New relationship types require a dictionary entry here via the extension lifecycle.

**What is written for you, and what is not.** Only one thing here is machine-maintained:
the **reverse views** in `System/Generated/reverse-relationships.md`, rebuilt by
`aios generate`. Every relationship field in the table above — `superseded_by` included —
is **authored**, by you or by the runtime following `safe-write`. No command edits a
note's frontmatter to add a reciprocal link.

This entry used to say the validator maintained `superseded_by`. It never did:
`System/Scripts/cmd/validate.py` performs **zero writes**, and its only supersession code
is the warning described above. A runtime that believed the doc left supersession chains
permanently dangling — the old record kept pointing nowhere while the gate stayed green.
If a reciprocal link is missing, a human or a runtime has to write it.

## Provenance and epistemic status

| Key | Type | Meaning |
|---|---|---|
| `confidence` | vocab | high / medium / low / unknown |
| `verification` | vocab | verified / corroborated / reported / **inferred** / unverified — inference is never presented as direct evidence |
| `provided_by` | text | (tacit sources) who supplied the recollection |
| `knowledge_type` | vocab | (tacit sources) firsthand-recollection, interpretation, political-context, … |
| `captured_at` | date | (sources) when the evidence was captured |
| `original_location` | text | (sources) URL or physical origin |

## Lifecycle and review

| Key | Type | Meaning |
|---|---|---|
| `review_due` | date | When this note should be re-verified. **There is no `decay` field in any schema** — the horizons live in `System/Registries/freshness.yaml`, per type, in days, and `aios review-due --set-missing` is the only thing that writes this date. Review is also triggered by upstream changes, access-time checks, and new `contradicts` links |
| `decided_at`, `decision_makers`, `review_condition` | — | decision class |
| `project` | id | decision class: scopes the decision to a project (one decisions space, per-project view generated — DEC-095). Link-checked like any relation |
| `stage`, `goal`, `due` | — | project class |
| `audience`, `delivered_at` | — | output class |
| `canonical_name` | text | entity class: the one authoritative name |
| `when_to_use` | text | procedure class |
| *(working class)* | — | no fields of its own — deliberately light (DEC-096): required are just id, type, subtype, created/updated, summary, status; bound to the projects folder (+ Inbox/Archive) — misplaced `working` is an error, a knowledge-typed note in the project layer is a rolled-up advisory (DEC-082) |

## Governance (DEC-008; `sync` added by DEC-092)

| Key | Vocab | Meaning |
|---|---|---|
| `classification` | public / internal / private / restricted | Sensitivity — who may read it. `restricted` means a compliant runtime must not retrieve or open it; in direct-file mode this is a binding rule, not physical confinement. Almost never what you want (see `sync`) |
| `domain` | work / personal / shared | Cross-domain retrieval is filtered before similarity or relevance |
| `ai_use` | allowed / local-only / prohibited | What any AI runtime may do with this content |
| `sync` | allowed / local-only | Storage boundary: may this file leave the machine via git push / cloud sync / hosted backup? `local-only` must be backed by a `.gitignore` rule (`aios validate` cross-checks both ways); a `Local Only/` folder implies it. Absence = allowed. Governs storage only — never retrieval (`ai_use`) or readability (`classification`) |
| `approval` | none / pending / approved / rejected | Human approval state for externally usable material |

## File classing and system fields

| Key | Meaning |
|---|---|
| `file_class` | canonical / generated / runtime-specific / temporary / example (Vault Profile §6; `example` is never retrieved as user truth — DEC-018) |
| `generated`, `generator` | Generated files: true + the producing component id. Never hand-edit |
| `schema_version` | The schema version the note was created under |
| `authority`, `canonical_for` | Documentation only: canonical/derived/generated; the rule domain a canonical doc owns |

## What never goes in frontmatter

Machine-operational data — file hashes, index timestamps, run results, validation caches — lives in `System/Generated/ops-registry.json`, produced by `aios.py generate`. Secrets never appear anywhere in the vault. Empty keys are omitted, not left blank.
